# 性能基线 — v0.1.2 RC

日期：2026-11-14 ｜ 环境：Windows / Node 22.22.2 / 本机原生进程（**非容器**）
数据集：`docs/performance-baseline.json` ｜ 脚本：`tests/scripts/perf-breakdown.mjs`

> 目的：回答 AC-05 的「端到端 1.22–1.30 超额来自哪里」。不修改任何验收阈值，不缩小负载规模。

## 1. 方法

单实例、`SEARCH_HUB_LOG_LEVEL=silent`、全局限流临时提高到 100000/min（仅压测实例；默认值仍是 300）。
1 个 mock provider（确定性 50ms 延迟，无网络）、`maxConcurrency=2`、3 把 Key（合计 6 个并发槽）。

| 场景 | 规模 |
|---|---|
| 顺序基线 | 200 次 `POST /api/search`，`limit=5`，`skipCache=true` |
| 突发 | 100 并发 × 3 轮，间隔为上一轮完成即开始 |

服务端 `stats.timing` 新增 `dbWriteMs`（本次为测量而加，长期保留）：覆盖任务初始 INSERT 与最终 task/event 持久化。

## 2. 顺序基线（200 样本，毫秒）

| 层 | P50 | P95 | P99 | 说明 |
|---|---|---|---|---|
| 客户端 wall | 61.9 | 64.0 | 75.4 | 含 HTTP 连接与客户端 JSON |
| 服务端 totalMs | 59.0 | 61.0 | 65.0 | `stats.timing.totalMs` |
| fanout | 59.0 | 61.0 | — | 单源，等于 total 的绝大部分 |
| fusion | 0.0 | 1.0 | — | 去重 + RRF |
| **dbWrite** | **0.8** | **1.5** | — | SQLite 两次写入合计 |
| HTTP 框架 + 序列化 | 2.6 | 4.2 | — | wall − totalMs |
| 排队 | ≈9.0 | — | — | fanout − 50ms provider |

**结论（顺序）**：SQLite 写入 **<1ms**、HTTP 框架开销 **2.6ms**、融合 **<1ms**。固定开销合计不到 5ms，不是瓶颈。9ms 的“排队”主要来自 Node 定时器粒度与事件循环调度，而非锁竞争（该 provider 只有 3 把 Key × 2 槽，顺序请求永远有空槽）。

## 3. 突发（100 并发 × 3 轮）

| 轮次 | wall | 服务端最大值 | 以 ⌈100/6⌉×50ms=850ms 计 ratioWall | 以单次中位 60ms 计期望 1020ms |
|---|---|---|---|---|
| 1 | 1179ms | 1020ms | 1.39 | 1.00 |
| 2 | 1123ms | 1002ms | 1.32 | 0.98 |
| 3 | 1070ms | 951ms | 1.26 | 0.93 |

- **服务端**最大单请求耗时 ≈ 17 波 × 单次实际 60ms ≈ 1020ms，与「单次中位数 × 波数」一致（ratio 0.93–1.00）。
- **客户端 wall** 比服务端最大值多 70–160ms，来自 100 条并发 TCP/TLS 之外的连接建立、fetch 调度与响应解析。
- 之前 QA 记录 1.22–1.30 的算法是「wall ÷（⌈100/6⌉ × 单次中位）」，分母用了 provider 标称/中位延迟；本轮把 **服务端 totalMs** 与 **客户端 wall** 分开后，可以看到：
  - 服务端流水线本身基本符合预算；
  - 超额主要来自**客户端并发建立连接的固定成本**（约 70–160ms/轮）以及 **mock provider 在并发下 50ms→60ms 的定时器漂移**；
  - SQLite（<1ms）、融合（<1ms）、日志（silent）均不是原因。

## 4. 日志开销

`silent` 与 `info` 的差异未单独跑两套实例（时间与端口隔离成本高），因此**不给出数字**。顺序基线显示服务端总开销仅 59ms（50ms provider + 6ms 调度 + <1ms DB + ~2ms 框架），即使日志翻倍也不会解释 200ms 级差异；该项标 **未测量**，不做推断。

## 5. AC-05 判定（不放宽）

AC-05 原文要求「总耗时 ≈ ⌈100/6⌉ × 单次延迟（±20%）」。用**客户端 wall** 计，三轮 ratio 1.26–1.39，仍超带；用**服务端 totalMs** 计，ratio 0.93–1.00，在带内。两种口径不一致，且本机是共享负载的 Windows 开发机。

因此 **AC-05 维持 PARTIAL**，缺口写清：
- 服务端流水线达标，客户端 wall 超带；
- 未在隔离 Linux / 容器内复测；
- 日志开销未单独测量。

**没有**修改 ±20%、没有减少 100 并发、没有更换 ratio 算法来制造 PASS。
