## 2. 目标、用户与非目标

### 2.1 Product Goals

1. **正确性**：消除重排序前截断、取消未传播、Deep 查询间未去重、多查询分数不可比、默认召回不足五类缺陷。
2. **可控质量**：用固定人工标注、同快照重排与真实联网对照证明 v0.1.18 相对 v0.1.17 的变化，不以合成 fixture 冒充真实质量。
3. **可解释与可降级**：路由和每个策略阶段可见；无付费 Key、无模型、无 Chromium 时明确说明受限能力，不伪造成功。

### 2.2 User Stories

1. 作为开发者，我用原有 `mode` 和响应字段完成搜索，以便升级后无需修改集成。
2. 作为研究者，我选择 Quality 或 Deep 策略，以便低排名但相关的结果不会在重排序前被永久截掉。
3. 作为实例管理员，我看到自动路由选中了哪个策略及命中规则，以便排查“为什么没有使用模型/某个源”。
4. 作为 Agent 集成方，我消费 SSE 或 NDJSON 的增量结果，并能严格区分临时结果与最终快照，以便提前展示且不重复计数。
5. 作为中文/英文混合查询用户，我保留原查询并指定检索语言，以便不因自动翻译丢失专有名词。
6. 作为管理员，我在搜索实验室比较 v0.1.17/v0.1.18，以便看到逐查询指标、排序变化和真实来源证据。
7. 作为运维者，正文读取默认不启动 Chromium，重任务在隔离 Runner 中限时限量执行，以便低内存实例稳定运行。
8. 作为运维者，系统根据实时资源压力自动收紧搜索、Deep、Embedding 与正文提取并发，以便高负载时仍能完成关键请求且不失控。

### 2.3 非目标

- 不重做安全、DR、发布流水线、Provider 插件体系或 UI 框架。
- 不训练模型，不提供“无限深搜”、自主浏览互联网或无人监督的循环 Agent。
- 不承诺所有网页可读；登录墙、付费墙、验证码、纯 Canvas 页面可返回明确失败。
- 不把自动路由描述为模型路由；不使用查询文本调用外部 LLM 来决定路由。
- 不删除或静默重写 v0.1.17 缓存；不以清空缓存制造升级兼容。
- 不将流式临时事件作为最终结果写入缓存、历史或评测。
- 不为资源内存治理引入常驻第二套监控 Agent，也不允许控制器覆盖管理员设置的硬上限。

## 3. 核心设计决策

### D1：策略与旧 `mode` 并存

新增可选 `strategy: "auto" | "fast" | "balanced" | "quality" | "deep"`。

- 只传旧 `mode`：走兼容路径，返回字段和默认值保持兼容；修复缺陷会改变错误结果，但不改变请求契约。
- 只传 `strategy`：按新策略执行，响应新增 `strategy`、`route`、`appliedStages`、`degradations`。
- 两者同时传：返回 400 `validation_error`，除非 `strategy` 与 `mode` 的等价映射完全一致；禁止存在两个静默竞争的开关。
- 都不传：保持现有默认路径（SettingsService 当前默认 `mode=basic`），不借升级改变所有旧客户端的成本与行为。
- `/api/search/deep` 继续强制 Deep；新增策略不得改变该端点的既有含义。
- MCP/CLI/Skills 使用同一共享 schema 和 SearchService；新增参数是可选字段，旧调用不变。

| 策略 | 召回与融合 | 模型阶段 | 默认预算/体验 |
|---|---|---|---|
| Fast | 单轮；默认 RRF；不做查询扩展 | 无 | 最低延迟，适合导航、精确 URL、简单关键词 |
| Balanced | 单轮；默认 RRF；按确定性规则启用可选扩展 | 仅配置且确有必要时启用 | 默认推荐的新策略 |
| Quality | 扩大并保留有界候选池；RRF 后 Rerank；无模型时明确降级为 RRF | Rerank 可选 | 适合研究、比较、模糊意图 |
| Deep | 多轮、多查询、跨查询去重与有界融合；可摘要 | 扩展/摘要可选，Rerank 可选 | 适合复杂问题，不是默认模式 |

### D2：有界候选池

不得“先截 `limit`，再重排序”。统一执行：

1. 最终 `limit` 为 1–100。单 Provider 允许召回至 `min(100, limit + 有界余量)`，默认余量为 3；显式 `perProviderLimit` 放宽到 1–100，旧 1–50 调用保持兼容。单 Provider、`limit=100` 时必须能返回 100 条。
2. 全局最多 8 个候选 Provider、每轮原始候选 400 条；多 Provider 不得突破该总上限。超出时按 Provider 稳定顺序轮流保留各源候选，并记录 `candidateTruncated`，不得静默丢弃。该限制适用于所有新策略，旧路径只修复正确性所需部分。
3. URL 规范化 + 同域近似标题去重后，**重排序输入上限 200 条**。选择按基础 RRF/基础排名确定，不能按标题随机丢弃。
4. Rerank/Embedding 每批最多 50 条，候选按确定性顺序分批；最终仅截取 `limit`（1–100）。
5. Deep 最多 4 个去重后的子查询、2 轮、32 个 Provider-query 调用、最多 64 个上游 HTTP 分页请求、总截止时间默认 30 秒且不超过 120 秒；先到先停。每次截断都返回计数和原因。
6. 所有中间集合必须有上限；禁止以 `Promise.all` 无界展开子查询、分页或模型批次。

### D3：可解释的规则型自动路由

`strategy="auto"` 只根据请求字段、Provider 能力/健康状态和本地配置决策：

- 显式 `deep` 意图、比较/多约束/研究类确定性信号 → Deep；否则复杂问题 → Quality；短查询/精确导航 → Fast；其余 → Balanced。
- 自动扩展须同时满足：Balanced/Quality/Deep、查询长度与词数达到阈值、用户未关闭 `queryExpansion`、存在可用扩展模型。
- 不使用向量相似度猜测用户意图，不发送查询给路由模型，不因商业 Provider 名称自动加权。
- `route` 必须返回 `selected`、`ruleId`、`matchedSignals`、`considered`、`decidedAt`，每次决策可复现。
- 管理员可在 Lab 中固定策略并重放同一请求；路由不能覆盖显式策略。

### D4：无付费 Key 的能力边界

| 能力 | 无付费 Key 时 |
|---|---|
| 公开/自托管搜索 Provider | 可用，遵循其限流与健康状态 |
| RRF、规则路由、去重、语言处理、正文 HTTP 读取、离线评测 | 可用 |
| Rerank / Embedding / LLM 扩展 / 摘要 | 不可用；新策略返回 `degradations` 并执行已声明的降级，不扣费、不报成功 |
| Deep 多轮 | 可执行有界多查询；LLM 扩展/摘要阶段标记跳过 |
| 真实联网质量评测 | 仅使用可用公开源；标注来源与 Provider 集合必须写进报告，不能外推为付费源质量 |
| 旧 `mode=rerank/embedding/...` | 保持既有 fail-fast（缺少模型 400），不能偷偷换成成功响应 |

## 4. 需求池

优先级：P0 = Stable 必须；P1 = 应随 Stable 交付，无法交付时需在发布说明明确限制；P2 = 后续增强。每项必须附自动化测试或可复现证据。

### P0：搜索核心正确性

| ID | 需求 | 验收标准 |
|---|---|---|
| C1 | 修复重排序前截断：先形成有界候选池，融合/重排序后再取 `limit` | 构造第 21–100 条含高相关结果，Rerank 后能进入 top 10；最终结果仍 ≤ `limit` |
| C2 | Embedding/Rerank 全链路传播取消与截止时间 | 任一在飞批次在 100ms 内收到 abort；无后续批次/分页发出；任务为 `cancelled`，不写缓存；不得写成 `failed` |
| C3 | Deep Search 跨查询去重 | 两个子查询返回同 URL/同域近似标题时只出现一次，但保留两个 `queryOrigins`；来源与分数不被覆盖丢失 |
| C4 | 多查询融合使用可比较分数 | 每查询先独立 RRF，再按命中查询数、查询权重与名次做归一化融合；不能直接累加不同查询的原始 RRF 分。相同输入顺序不改变结果 |
| C5 | 默认召回修正 | 省略 `perProviderLimit` 时满足 D2；多 Provider 场景不会得到过小默认值；显式值不被覆盖 |
| C6 | 阶段与失败可观测 | `stats` 增加原始/去重/候选/重排序/返回计数、各阶段耗时、跳过原因；计数恒等式可核对 |

| ID | 需求 | 验收标准 |

| S2 | 规则型自动路由 | 同一输入/配置连续 100 次决策一致；返回完整规则解释；不产生模型调用 |

### P0：统一正文读取与流式

| ID | 需求 | 验收标准 |
|---|---|---|
| W1 | 统一网页正文读取服务 | REST/MCP/CLI/Skills 返回相同正文 schema；至少覆盖文章、正文列表、编码与超长页；原始 HTML 不默认返回 |
| W2 | 默认不启动 Chromium | 普通 HTTP 路径无 Chromium/Playwright 进程；测试断言启动次数为 0。仅 `render=true` 且管理员启用时允许浏览器渲染 |
| W3 | 读取安全与限制 | 复用 SSRF/重定向校验；默认最多 2 MiB、10 秒、5 次重定向；拒绝非文本类型；超限返回 `truncated`，失败返回稳定错误码，不返回 500 |
| W4 | 真 SSE | `POST /api/search/stream` 使用 `text/event-stream`，禁止缓冲；首批元数据 ≤1 秒，Provider 返回后即可增量推送；15 秒心跳 |
| W5 | 真 NDJSON | 同一服务可输出 `application/x-ndjson`，每行一个完整 JSON；客户端断开即取消上游；无伪进度定时器 |
| W6 | 临时/最终结果严格区分 | 临时事件含 `sequence`、`final:false`；唯一 `done` 事件含 `final:true` 和完整最终快照，与非流式同输入结果一致；临时结果不缓存、不入历史、不参与指标 |
| W7 | 流式边界 | 缓存命中发最终结果与 `done`，不伪造增量；取消发终止状态且无最终成功快照；错误后连接终止；序列号单调递增 |

## 5. API/UI 兼容性与契约

### 5.1 REST / MCP / CLI / Skills

- 保留 `POST /api/search`、`POST /api/search/deep`、任务查询/取消及现有响应字段。
- 新增 `POST /api/search/stream`；Deep 流式沿用同一实现并强制 Deep。
- 请求新增字段均为可选：`strategy`、`stream`（`sse`/`ndjson`）、`queryExpansion`、`maxSubqueries`、`maxRounds`、`render`。
- 新增正文读取：`POST /api/web/read`，请求 `{url, render?, maxBytes?, timeoutMs?}`；MCP 工具 `read_webpage`、CLI `shub read <url>`、Skill 均调用该服务。`search` scope 可用，渲染能力可单独受管理员开关限制。
- SSE 事件：`meta`、`results`、`status`、`done`、`error`。NDJSON 用 `type` 表达同语义。`results` 必须含 `final:false`；`done` 必须含 `final:true`、`sequence`、`status`、`results`、`summary`、`stats`、`errors`、`failedSources`、`strategy`、`route`。
- 流式响应不得改变非流式最终结果；两者共用终止与序列化逻辑。
- 请求校验失败发生在开流前；开流后的错误使用流内错误事件，不能混入第二个 HTTP 状态。
- OpenAPI、MCP schema、CLI help、Skill 文档同批更新。

### 5.2 UI

- 搜索页增加策略选择（自动/Fast/Balanced/Quality/Deep），默认展示旧模式兼容入口；显示实际策略、命中规则、跳过阶段和候选计数。
- 流式结果区显示“临时结果”，收到 `done` 后替换为最终结果并清除临时标记；不得将临时卡片累加成最终列表。
- 实验室新增“搜索实验室”入口，复用现有 MUI Tabs/Card/Table/Drawer；四策略对比、路由回放、逐查询指标、排序位移、来源证据均可查看。
- 设置页增加资源预算与并发硬上限；状态区展示自动收紧/恢复原因。正文读取显示实际提取器和是否发生截断。
- 中英文同步；不以颜色作为唯一状态信号。

## 6. 搜索实验室后台

### 6.1 能力

1. **路由回放**：输入请求与冻结配置，输出选中策略、规则、候选预算，不访问付费模型。
2. **实验执行**：`snapshot` 模式复用冻结的 per-provider 结果；`live` 模式走生产 SearchService、Key 池、限流与 SSRF 链路。live 必须显式确认预算。
3. **对比**：同一查询集、qrels、top K、去重与公式下比较 v0.1.17/v0.1.18；输出整体、分类、逐查询指标及 entered/exited/moved。
4. **失败可见**：Provider 失败、空结果、未标注、低样本、预算耗尽均独立显示；不得用 0 代替 N/A。

### 6.2 建议接口

```
GET    /api/admin/quality/search-lab/capabilities
POST   /api/admin/quality/search-lab/route-preview
POST   /api/admin/quality/search-lab/runs
GET    /api/admin/quality/search-lab/runs/:id
POST   /api/admin/quality/search-lab/runs/:id/cancel
GET    /api/admin/quality/search-lab/compare?baseline=&candidate=
```

所有接口 admin；写操作 CSRF；`search` scope Token 403。运行记录包含实现 commit、策略/规则版本、Provider 非密配置指纹、模型指纹、qrels 指纹、请求预算、实际请求数、缓存命中与退化原因。密钥永不进入指纹或报告。

## 7. 真实质量评测与 v0.1.17 对比

### 7.1 数据与公平性

- 冻结至少 **40 条真实公开查询**：中英文各至少 12 条，覆盖导航、事实、比较、技术、新闻/时效四类；不得用 synthetic fixture 证明本轮质量提升。
- 由至少两名人工标注者对基线/候选结果并集（每查询 top 20）按 0–3 标注，分歧仲裁；保留 `human` 来源与 qrels 指纹。Recall 仅在标注完整时计算。
- 固定查询集、数据版本、qrels、top K、去重口径和指标公式；冻结 v0.1.17 实现与 v0.1.18 实现，记录 exact commit。
- 两层证据：**同快照重排**隔离算法变化；**真实联网配对运行**验证端到端，并记录时间窗、来源、失败和缓存开关。两次独立 live 抓取不得包装成同快照证据。
- 查询不得在 development/holdout 间泄漏；如调参，只用 development，最终结论在 holdout 上一次性验证。

### 7.2 指标与发布门槛

- 主指标：nDCG@10；辅助：MRR@10、P@10、Recall@20（完整标注时）；护栏：空结果率、部分失败率、重复率、P50/P95 延迟、上游请求数。
- 总体有效查询 ≥24，分类有效查询 ≥8；低于门槛输出 `INSUFFICIENT_EVIDENCE`，不输出胜负。
- 目标：holdout 平均 nDCG@10 相对 v0.1.17 **提升 ≥0.03**，配对 bootstrap 95% 置信区间下界 >0；MRR@10 下降不超过 0.01。
- 任一预注册分类 nDCG@10 下降 >0.03、空结果率上升 >1 个百分点，或 P95 延迟上升 >20%，均需说明原因并重新评审；不得只报平均值。
- 报告必须列出改善/退化查询、失败查询、未标注比例、实际 Provider 与所有降级。若无付费 Key，结论限定于实际使用的公开/自托管源。
- CI 只跑 offline 回归；真实 live 评测作为发布证据单独保存，不依赖收费服务才能完成 CI。

## 8. 资源内存治理与隔离 Runner

### 8.1 资源内存自动治理

- 继承现有 `resource-doctor`、资源快照与测试低内存工具，不新建第二套监控体系；治理对象是进程资源，不是用户搜索记忆。
- 输入信号包括 RSS、堆使用、事件循环/队列等待、在飞请求、Worker 数和可用内存；采样失败时保持上一次安全预算并记录原因，不得假设内存充足。
- 控制器动态调整：Agent 任务并发、Vitest Worker 数、Playwright 并发、构建并发、搜索 Provider 并发、Deep 子查询并发、Embedding 批大小、正文提取并发。
- 每类资源必须有最小/最大值与恢复滞回；压力上升时先降并发和批次，达到硬阈值时拒绝新任务并返回可重试错误；压力解除后逐步恢复，禁止频繁振荡。
- 管理员手动设置的值是硬上限，自动控制器只能进一步收紧，不能越过；测试/构建命令与生产搜索共享同一预算契约，但不得互相无限争抢。
- 资源事件只记录预算、实际值、原因和任务类型，不记录查询正文、网页内容或凭证。

### 8.2 隔离 Runner

- 使用 `worker_threads` 执行正文规范化、离线评测等 CPU 密集任务；不执行任意用户代码、shell 或未签名插件。
- 默认最多 2 个 Worker；单任务 CPU 超时 5 秒、堆内存上限 128 MiB、输入/输出字节有界；超限终止 Worker。
- 失败返回稳定错误 `runner_unavailable`，记录任务类型与资源原因，不泄露路径、查询或堆栈；不得回退到无界主进程。
- Chromium（P1）必须独立进程/上下文，复用相同超时、并发、出站与内存限制；默认不安装/下载浏览器。

## 9. 验收与发布口径

### 9.1 P0 验收清单

- [ ] 五类核心 Bug 均有失败红测与修复绿测；取消不产生缓存/后续请求。
- [ ] 四策略、规则路由、旧模式兼容和越界参数测试通过。
- [ ] 候选池、Deep 查询数/轮数/请求/时间上限均有压力测试，低内存测试通过。
- [ ] REST/MCP/CLI/Skills 的请求、正文读取与最终响应契约一致。
- [ ] SSE/NDJSON 真增量、心跳、断开取消、缓存命中、错误与 `final` 语义测试通过。
- [ ] v0.1.17 SQLite 升级后缓存保留且兼容命中；新指纹隔离测试通过。
- [ ] 正文读取默认路径 Chromium 启动次数为 0；安全与截断用例通过。
- [ ] 资源压力升高时各类并发/批次按预算下降，解除后滞回恢复；手动硬上限不可被越过；Runner 超时/超限可恢复。
- [ ] 真实质量报告满足 §7 或明确标记证据不足；禁止以合成数据替代。
- [ ] `typecheck`、`lint`、全量测试、构建、既有发布门禁通过；无新增高危依赖或密钥泄漏。
- [ ] API、MCP、CLI、Skills、缓存与质量文档同步；CHANGELOG 标注兼容性变化。

### 9.2 Stable 发布口径

- 版本统一为 **v0.1.18 Stable**，不移动旧 tag，不重复发布；以 exact-SHA 构建产物和发布证据为准。
- 发布说明必须分别列出：Bug 修复、新增能力、默认行为变化、无 Key/无浏览器限制、缓存兼容性、真实评测结论与已知限制。
- 只允许声明已被证据支持的质量提升；若 live 数据不足，写“离线/部分来源验证”，不得写“全面质量提升”。
- 回滚不得删除新数据库字段或缓存行；旧版本仍能打开升级后的数据库。流式与正文读取为新增入口，旧入口保持可用。

## 10. 待确认事项

1. **资源预算初始值**：各类并发的默认上下限需结合既有 `resource-doctor` 基线确定；无论取值如何，动态收紧、手动硬上限和滞回恢复均为 P0。
2. **真实评测 Key**：发布前由主理人确认可用的公开/自托管 Provider；不得为评测临时购买或使用个人付费 Key。
3. **浏览器渲染**：v0.1.18 是否随 Stable 启用 P1 的 `render=true`；未启用时必须保持开关关闭并在 API/UI 明示。
4. **质量门槛执行**：若 holdout 达不到 §7 目标，需在“修复正确性但不宣称质量提升”与“延后 Stable”之间由主理人明确决策，不能静默降低阈值。
5. **Deep 默认预算**：默认 4 查询/2 轮/32 次 Provider-query 为产品上限；若真实 Provider 分页成本更高，以更严格的 64 次 HTTP 上限为准。
