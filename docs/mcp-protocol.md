# MCP 协议版本：实测结果与实现边界

本文记录的是**实测**，不是文档转述。所有数字都可以用
`node .data/audit/mcp-version.mjs` 或后台 `GET /api/admin/mcp` 复现。

## 一、实测：SDK 支持到哪一个修订

安装的 SDK：`@modelcontextprotocol/server@2.4.0`（npm `latest`，
发布时间 2026-10-23）。

SDK 自带的常量：

```
LATEST_PROTOCOL_VERSION = "2025-11-25"
SUPPORTED_PROTOCOL_VERSIONS = [2025-11-25, 2025-06-18, 2025-03-26, 2024-11-05, 2024-10-07]
```

对运行中的服务发 `initialize`，观察实际协商结果：

| 客户端请求 | HTTP | 实际协商 | 结论 |
|---|---|---|---|
| `2025-11-25` | 200 | `2025-11-25` | 支持 |
| `2025-06-18` | 200 | `2025-06-18` | 支持 |
| `2026-07-28` | 200 | **`2025-11-25`** | **不支持，被降级** |
| `2099-01-01` | 200 | `2025-11-25` | 未知版本一律降级 |

**因此 v0.1.5 不声称支持 2026-07-28。** 它确实"能连上"，但那是被降级到
2025-11-25 之后的连接。把版本号写死成最新日期就能"兼容"是一种假象，而且会让
依赖 2026 新语义（无状态请求）的客户端得到与预期不同的行为。

后台的 `revision2026Supported` 字段直接读 SDK 常量、并与实测结果一致，
升级 SDK 之后它会自动变 `true`，不需要改代码或改文案。

## 二、三种"更新"不是一回事

| 类型 | 含义 | 需要做什么 | 当前状态 |
|---|---|---|---|
| A 协议协商 | 服务端与客户端按双向支持选版本 | 什么都不用装 | 已自动进行 |
| B SDK 升级 | 新修订由新 SDK 实现 | 换依赖 → 重建 → 重跑协议测试 | 2.4.0 已是最新，无可用升级 |
| C 程序升级 | Search Hub 自身新版本 | 安装经过验证的发布包 | 已实现检查与暂存，安装由启动器执行 |

后台把这三类分开显示，不复用同一个"有更新"角标。

## 三、`tools/list_changed` 为什么不发

本服务的工具目录是**静态**的：12 个工具在进程启动时全部注册完毕。

- 新增/启用/禁用一个 **Provider 实例**改变的是搜索结果来源，不是工具目录。
- 因此发 `tools/list_changed` 会让客户端重新拉取一个不可能变化列表，
  属于虚假通知。
- 只有工具目录真的变化（例如随机型/配置启用新工具）才应该发；当前没有任何
  这样的开关，所以**不发**是正确的实现，而不是"还没做"。

`sdk` 自身支持 `ToolListChangedNotification`，一旦引入动态工具，可以立即接上。
