## 0. 结论先行

- **Phase 1 的一句话定义**：单机自托管、自备 Key、多源并发搜索 + Key 三级额度守护 + 融合结果可被 REST / MCP（HTTP+stdio）/ Agent Skills 三种方式调用，且全部配置重启不丢、密钥不泄漏。
- **范围**：14 条用户故事，12 条 Must（含 Agent Skills；US-14 AI 可选增强为 Should）；多实例协调、语义去重**本期不做**；结果缓存实现为**默认关闭**的可选项，验收与实验室始终绕过缓存（见 §6 Q6）。
- **已裁决要点**：Key 额度 = 并发 + rpm + 日配额三控；Provider = Brave + SearXNG 真实源 + Generic + Mock；MCP = HTTP + stdio（stdio 代理同一 REST）；Skills 本期交付 3 个 SKILL.md；鉴权 = 管理员 scrypt + HttpOnly Cookie + CSRF + 可撤销 API Token。
- **模型能力口径（v0.4 按主理人纠正）**：AI/Embedding/Rerank 是**真实可用的可选增强，不是骨架**——Chat（OpenAI 兼容 / Anthropic / Gemini）、Embedding（OpenAI 兼容 / custom-http，含维度校验）、Rerank（Cohere/Jina 兼容 / custom-http）均为真实 HTTP 调用；查询改写、带 `[n]` 引用的摘要、提示词注入检测均已实现并在可选阶段调用。**默认关闭（`mode=basic`），未配置模型时基础搜索完全不受影响**；配置后由 `mode` 决定启用。真实第三方联调待 Key，属"未联调"，不属"未实现"。
- **Q7 已定案（架构 §3 + 本文 AC-12）**：SQLite WAL + 合批写（250ms/200 条），额度按**实时内存计数**严格判定、不打折；统计一致性降为**请求结束后 5s 内最终一致**。**Q10 已追认**：崩溃丢额度热状态接受"启动校准 + 文档披露"，不做同步落库；`docker restart` 须 flush，kill -9 不在承诺内。
- **4 条不可让步的验收红线**（任何一条不达标即 Phase 1 未完成）：
  1. 100 并发下，单 Key **并发/rpm/日配额三级额度突破 0 次**；额度拒绝有明确错误码，不静默丢弃；且并发确实发生了（不同 Key 时间窗重叠）。
  2. 单源故障（超时/401/429/5xx）时，整体请求成功率 **≥ 99%**，且失败源在响应与实验室中**可见**。
  3. 明文密钥在 API 响应、应用日志、DB 文件中出现 **0 次**。
  4. 容器重启后源/Key/模型配置与累计统计保留率 **100%**（用非默认值验证，不比对默认值）。

## 1. 问题定义

- **目标用户**
  - U1 自托管部署者（个人开发者 / 2-5 人小团队）：手握 Brave、Tavily、SearXNG 等一个或多个搜索 Key，想要"一套服务、多个数据源"。
  - U2 Agent 构建者：需要通过 REST / MCP 把搜索能力接进自己的 Agent、IDE、Chat 客户端。
- **核心场景（1-3 个）**
  - **S1 一次部署、长期调用**：`docker compose up` → 用一次性 setup token 设管理员口令 → 配 2-3 个源与多 Key → 用 curl、MCP 客户端或 Agent Skill 调 `/api/search` 拿到去重融合后的结果。触发时机：搭自己的检索底座时。
  - **S2 搜索实验室调参**：集成方对同一 query 换源组合、调 `topK`/去重阈值/RRF `k`/超时预算，**当场看到每个源的原始条数、耗时、错误码、融合前后变化**。触发时机：结果不理想或接入新源时。
  - **S3 额度与稳定性守护**：多 Key 轮转 + 每 Key 并发/rpm/日配额三级上限 + 失败冷却；某个源挂掉或额度耗尽，整体仍返回其他源的结果。触发时机：7×24 被 Agent 自动调用时。
- **现有替代方案与痛点**
  | 替代方案 | 痛点 |
  |---|---|
  | 直接用单家搜索 API | 单点额度墙、单点故障、结果单一、无法融合排序 |
  | 自研聚合脚本 | 无 Key 池/限速/冷却，额度易被击穿；去重与融合口径各写一套；无法被 Agent 标准调用 |
  | SaaS 聚合搜索 | Key 与 query 托管在第三方，数据与成本不可控，不能自托管 |
  | 检索库（LangChain 类） | 是库不是服务：无管理面、无运行时用量/健康可观测性、多 Key 与额度需自己写 |
- **成功标准（可度量）**
  - TTFV（`compose up` → 首次 `/api/search` 返回非空结果）**≤ 10 分钟**，含首次引导（读取自动生成的 setup token）与自行设置管理员口令。
  - 100 并发同一源组：并发/rpm/日配额突破次数 **= 0**，且不同 Key 调用时间窗确有重叠。
  - 注入单源故障的 200 次请求：整体成功率 **≥ 99%**。
  - 明文密钥泄漏命中数 **= 0**（响应/日志/DB 三处扫描）；无默认口令、Session Cookie 可验证为 HttpOnly。
  - 容器重启后配置与统计保留率 **= 100%**。
  - MCP（HTTP 与 stdio 双通道）与 3 个 SKILL.md 均可完成一次真实搜索，返回 **≥ 1 条**结构化结果。

### 3.2 本期不做（Out of Scope）与原因

| 不做项 | 原因 | 归属阶段 |
|---|---|---|
| 多轮对话式检索（会话记忆） | 单轮检索已闭环；多轮需要会话状态与上下文预算，属独立命题 | Phase 2 |
| Embedding 向量**持久化索引**（跨请求语义库） | 本期 Embedding 只用于单次请求内的语义打分，不建向量库 | Phase 3 |
| 模型效果调优 / 提示词迭代 / 真实第三方联调 | 无 Key、无评测集，无法客观判定质量；本期只保证**链路能跑通且可降级** | Phase 2 |
| 更多 Provider（超出 Brave / SearXNG / Hacker News / Generic / Mock） | 适配器成本线性增长，先用 Generic 兜底覆盖长尾 | Phase 4 |
| PostgreSQL 支持 | 单机单用户无收益，反而增加部署门槛 | Phase 4 |
| Redis / 多实例协调、分布式限速 | 单进程内额度已可硬保证；跨实例一致性是独立命题 | Phase 5 |
| 多租户/团队权限、计费、审计合规 | 自托管单用户场景不需要，过早引入会拖慢闭环 | Phase 5 |
| 语义去重（相似度阈值） | 阈值无标注数据无法定标，先做 URL 归一化去重 | Phase 3 |
| 结果缓存/热门查询预取 | 会掩盖真实延迟与额度行为，干扰验收；实现已存在但**默认关闭**，搜索实验室强制 `skipCache` | Phase 3 才评估是否默认开启 |

### 3.4 验收标准表（AC-01 ~ AC-16，Phase 1 判定依据）

标注 **【红线】** 的四条为不可让步项。"验证方式"中"自动"= 可进 CI 的用例；"人工"= §8 脚本内 5 分钟内完成。

| ID | 检查项 | 判定阈值 / 期望结果 | 验证方式 |
|---|---|---|---|
| AC-01 | 首次安装与就绪 | 镜像基线 **`node:22-bookworm-slim`（Node ≥ 22.12**，better-sqlite3 使用官方预编译产物、无需 node-gyp）；`compose up` 到 `/api/health` 200 ≤ 120s（冷启动含拉镜像不计）；未配置任何源时后台显示"未就绪"而非"已完成"；首次引导要求**一次性 setup token**（自动生成到 `data/setup-token` 或由 `SEARCH_HUB_SETUP_TOKEN` 指定）并**自行设置**管理员口令，系统无任何默认密码/预置凭据；无 token 的 setup 请求必须 403 | 自动 + 人工 |
| AC-02 | 源添加与连通性自检 | Brave 与 SearXNG 各自返回明确结论（OK 或 错误码+原因）；错误 Key 必须返回失败且该源不可置为"启用"；自检耗时 ≤ 10s | 自动 |
| AC-03 | 多 Key 与掩码 | 添加 3 Key 后列表仅显示掩码（首 4 + 末 4）；任一配置导出/查询接口不含完整 Key | 自动 |
| AC-04 | **【红线】密钥不泄漏** | 响应全字段递归扫描 + 全部日志 grep + DB 文件明文/Base64/Hex 三重扫描 + 异常堆栈与请求快照，命中数**全部为 0** | 自动 |
| AC-05 | **【红线】三级额度不被突破** | 100 并发打同一源（3 Key × `maxConcurrency=2`）：每 Key in-flight **峰值恰为 2**，突破 **0**；`rpm` 窗口内请求数 **≤ rpm**（实测 rpm=10 时任意 60s 窗口 ≤ 10）；总耗时 ≈ ⌈100/6⌉ × 单次延迟（±20%），显著小于串行的 100 × 延迟；不同 Key 的调用时间窗**确有重叠**（证明并发真实存在）。**判定基准 = 实时内存计数，不因异步落库而放宽或延后**；排队超时须返回 `queue_timeout` + 503，不得静默丢弃 | 自动（Mock 时间戳） |
| AC-05b | 搜索实验室明细 | 单次调试 5s 内返回：每源原始条数、耗时、错误码、去重前后条数、RRF 前 10 名及分数 | 自动 + 人工 |
| AC-06 | **【红线】单源故障不影响整体** | 注入超时/401/429/5xx/畸形 JSON 各 50 次：整体成功率 **≥ 99%**；`failedSources` 精确等于故障源集合且含原因码；单次请求 ≤ 超时预算 + 500ms | 自动 |
| AC-07 | MCP 双通道可调用 | 三断言：(1) Streamable HTTP 与 stdio **均**可 `list tools` 并调用搜索，同一 query 的结构化字段一致（`results[].url/title/source` 逐项相等）；(2) **stdio 为代理**——服务端日志可见对应 REST 请求（携带 Token）；(3) **关停 REST 进程后 stdio 调用必须失败**（证明不是第二套实现，R6 判据固化）；非法参数返回可读错误、进程不退出 | 自动 + 人工 |
| AC-08 | 限流冷却与全冷却 | 429 后 30s 内该 Key 不再被选中且状态可见；日配额耗尽同理；全部 Key 不可用时返回 503 + 明确错误码（非空结果） | 自动 |
| AC-09 | **【红线】重启后配置保留** | 写入非默认值后 `docker restart`：配置逐项相等（100%）、迁移版本不变、累计调用数不归零。**SIGTERM 时必须 flush 写缓冲**（250ms 批次的未落盘数据不得丢；`docker restart` 属优雅停机，须与 kill -9 区分，后者不在承诺内） | 自动 |
| AC-10 | 去重与 RRF 正确性 | 同 URL 变体（utm/尾斜杠/大小写）合并为 1 条；固定 fixture 手算分数一致（容差 1e-6）；打乱输入顺序两次结果不变 | 自动 |
| AC-11 | 鉴权与会话 | 未登录访问管理 API → 401；错误口令 → 401 且不泄漏"是否存在该用户"；登录后 Cookie 为 `HttpOnly`（响应头可验证）；缺 CSRF Header 的写操作 → 403；API Token 可撤销，撤销后立即 401；Token 带 scope 越界 → 403；仅 `/api/health` 免鉴权 | 自动 |
| AC-12 | 统计一致性（**最终一致**） | 请求结束后 **5 秒内**，仪表盘 24h 调用数、每源成功率、每 Key 用量与 DB 聚合结果一致（5s 是上限，不是平均值；超时即不达标）。其余断言（成功率、去重前后条数、失败源集合）仍**即时精确**判定 | 自动（写入后 5s 轮询断言） |
| AC-13 | Agent Skills 可用 | 3 个 SKILL.md 存在且被 MCP 客户端成功加载；按文档执行可完成一次真实搜索（含 Token 注入步骤）；文档内无 `TODO`/占位符/示例域名失效；调用失败时文档给出的排错步骤可定位到具体错误码 | 人工（≤ 5 分钟/个） |
| AC-14 | 未实现能力不可被当成可用（**只管目录条目，不管模型路由**） | 能力目录中 `implementation=planned` / `unavailable` 的条目：UI 标注"仅目录 · 未实现"、**创建按钮不可用**（`disabled` 或不存在）；直接调创建 API 返回 409/400 + 明确 code（不返回 5xx、不静默成功）；这类条目不出现在可选源列表中。**模型配置页与模型路由不在本条约束范围内**（见 AC-16） | 自动（DOM + API）+ 人工 |
| AC-15 | 能力目录与可用源不混淆 | UI 源列表与发布说明中：「已实现」仅标注 Tavily / Bocha / Brave / SearXNG / Hacker News / Generic / Mock；目录条目另区呈现并注明"仅目录 · 未实现"；页面不存在"支持 30 源"类暗示性文案（对 DOM 文案做关键字断言） | 自动（文案扫描）+ 人工 |
| AC-16 | **模型为可选增强，且真实可用、可降级** | (1) **默认关闭**：`mode=basic` 或未配置模型时，`/api/search` 结果与无模型时逐字段一致，且**零模型出站请求**（网络桩/日志断言）；(2) **配置后可用**：配 Chat 模型 + `mode=rerank_summary` → 返回带 `[n]` 引用的摘要，每个 `[n]` 能在 `results` 中定位到对应条目；配 Embedding/Rerank 模型 → 对应阶段真实生效；(3) **可降级**：模型超时/401/畸形响应 → 返回空摘要 + `degraded=true`，搜索结果照常 200（不 5xx、不整单失败）；(4) **测试按钮真实**：模型"测试"必须发出真实 HTTP 请求——用错误 Key 测试必须返回失败（返回"成功"即判作弊）；(5) **注入防护**：含"ignore previous instructions"等片段的摘要输入被标记（`findings` 非空）且不被静默剥离 | 自动 + 人工（需真实 Key 的项标注"未联调"） |

## 4. 人机边界（如涉及 AI）

Phase 1 **默认路径不含模型推理**（`mode=basic`）；模型只在用户显式配置并选用带模型能力的 `mode` 时参与，且任一环节失败必须降级为确定性结果。

| 环节 | 执行方 | 理由 | 兜底策略 |
|---|---|---|---|
| 源选择与并发调度 | 确定性代码 | 规则可完全表达，模型只会引入不确定性 | 失败降级为按优先级顺序执行 |
| Key 轮转/并发与速率限制/冷却 | 确定性代码（硬约束） | 额度是硬性契约，模型判断不可审计 | 计数超限直接拒绝（503 + code），不排队静默丢请求 |
| 鉴权/会话/Token 校验 | 确定性代码 | 安全判定不可概率化；口令哈希与会话由代码保证 | 校验失败一律 401/403，不放行、不降级为匿名 |
| 去重与 RRF 融合 | 确定性代码 | 需可复算、可断言、顺序无关 | 输入异常时降级为不融合但返回原始分组 |
| 连通性诊断与错误码映射 | 确定性代码 + 人工复核 | 错误码覆盖不到的长尾需人看原始响应 | 保留原始响应片段（已脱敏）供实验室查看 |
| 参数调优（topK/去重/RRF k/超时） | 人工（搜索实验室） | 属业务偏好，不做自动决策 | 提供默认值与"恢复默认" |
| 查询改写 / 摘要（含 `[n]` 引用） | 智能体/LLM（**可选，默认关闭**） | 生成类任务适合模型 | 失败返回空摘要 + `degraded=true`，原文结果始终保留；摘要不得成为唯一结果 |
| 语义打分 / 重排 | 智能体/LLM（Embedding/Rerank，**可选**） | 排序与相似度属模型擅长项 | 模型缺失或失败 → 回落到 RRF 顺序，不阻断返回 |
| 提示词注入检测 | 确定性代码（正则规则，**标记不剥离**） | 安全判定要可复算、可审计；模型自检不可信 | 检出仅写入 `findings` 供上游决策，不静默改写结果 |

> MCP 侧边界：是否调用搜索、如何串联多轮，由客户端 Agent 决定；本平台不自主发起搜索。

## 7. 反作弊检查清单（验收时必跑）

> 原则：**不信任"看起来对"**。每个用例都要有一条"若实现是假的，哪一步会露馅"的断点。

| # | 最可能被"假装完成"的风险点 | 假完成的典型表现 | 反作弊检查方法 | 判定 |
|---|---|---|---|---|
| R1 | **并发额度"靠串行化"达标** | 全局锁让并发=1，额度自然不超，但吞吐是假的；或只管并发不管 rpm | Mock Provider 对每次调用记录 enter/exit 纳秒时间戳；注入 50-200ms 随机延迟；断言 ①max overlap == `maxConcurrency`（不是 1，也不是上限+1）②总耗时 ≈ ⌈N/上限⌉×单次延迟 而非 N×延迟 ③不同 Key 的调用时间窗确有重叠 ④把 rpm 调到 3 后连打 20 次，第 4 次起必须被拒（证明速率控制真实生效，而非只做了并发） | 四条全过 |
| R2 | **单源故障"假隔离"** | try/catch 吞异常，整体返回 200 但 results 为空/只剩缓存；或故障源仍被反复调用拖垮整体 | 用可控故障桩（超时/401/429/5xx/畸形 JSON 各 50 次）；断言 ①健康源结果条数 > 0 ②`failedSources` 精确等于故障源集合且含原因码 ③故障源在冷却后被"跳过"而非每次重试（`skipped` 计数 > 0） ④去掉故障源后同一 query 的结果条数不少于故障时 | 四条全过 |
| R3 | **密钥"表面脱敏"** | 只在 API DTO 里打码，日志/DB/错误堆栈仍明文 | 用带唯一指纹的假 Key（如 `sk-TEST-<uuid>`）；跑完搜索后：①对所有 API 响应体递归取全部字符串 ②`grep -r` 全部日志 ③对 SQLite 文件做明文 + Base64 + Hex 三重扫描 ④触发一次 provider 异常，检查错误堆栈/请求快照 | 四处命中数均为 0 |
| R4 | **"假持久化"** | 重启后显示默认值，恰好与"刚初始化"看起来一样 | 写入**非默认值**（自定义源名、随机 UUID 标签、日配额=7、rpm=3、`maxConcurrency=1`），`docker restart`（非进程重启）；断言逐项相等且 DB 迁移版本不变；再断言重启后**累计调用数**仍等于重启前计数 | 全部相等，且计数器不归零 |
| R5 | **融合/多源"假实现"** | 多源其实只调了一个源；去重只做全等 URL；RRF 用固定顺序或写死分数 | ①用 3 个返回**可区分指纹**的桩源，断言响应中 3 个 `source` 均出现且 `provider_call_total` 各 +1 ②两源返回同 URL 但 utm/尾斜杠/大小写不同，断言合并为 1 条 ③固定 fixture 手算 RRF 分数（容差 1e-6）并打乱输入顺序两次，断言排序与分数不变 ④断言某条只在源 B 出现的结果名次符合 RRF 预期（而非固定拼接） | 四条全过 |
| R6 | **MCP "复制第二套实现"** | stdio 里另写一份搜索逻辑，与 REST 行为漂移；或只做了 HTTP，stdio 是摆设 | 同一 query 分别经 HTTP 与 stdio 调用，逐字段比对（`results` 的 url/title/source 完全一致）；关掉 REST 服务后 stdio 调用**必须失败**（证明它是代理而非独立实现）；stdio 调用期间服务端日志应出现对应 REST 请求记录 | 三条全过 |
| R7 | **"未实现条目"被当成可用** | `planned`/`unavailable` 的源在 UI 可创建，或直接调创建 API 也成功；或报 500 看不出是"没实现" | ①对目录里每条 `planned`/`unavailable`：UI 创建入口 `disabled` 或不存在；②直接 `POST` 创建该类型 → 返回 409/400 + 明确 code（不是 5xx、不是 200）；③该类型不出现在 `/api/search` 的可选源列表里 | 三条全过 |
| R8 | **"目录 N 源"暗示可用** | 能力目录里 28 个条目被 UI 当作可选源展示，或文案写"支持 30 源/N 源" | DOM 文案关键字断言：不存在"30 源/支持 N 源"类表述；目录条目单独分区并注明"仅目录 · 未实现"；只有 Tavily / Bocha / Brave / SearXNG / Hacker News / Generic / Mock 出现在"已实现"区 | 全过 |
| R9 | **模型"假可用"或"假不可用"**（D-1 纠偏后新增） | 两种相反作弊：①测试按钮不发真实请求却返回"成功"，或摘要写死/回显 query 冒充模型输出；②反过来把"没配模型/没联调"说成"未实现"来规避功能验收 | **正向**：错误 Key 调 `/api/admin/models/:id/test` 必须失败；配真实 Key 时上游日志可见对应请求；`mode=basic` 时模型出站数必须为 0（证明默认真关闭）。**反向**：直接调模型测试/搜索（带模型 mode）路由，不得返回 501/"not implemented"；摘要在无模型时必须 `degraded=true` 而非编造文本 | 两组全过 |
| R10 | **可选阶段拖垮主流程** | 模型报错被当成整单失败，或摘要把 `results` 替换掉 | 用 401/超时/畸形响应的模型桩：断言 ①HTTP 仍 200 ②`results` 条数与无模型时一致 ③`summary.degraded=true` 且 `summary.text` 为空（不是编造内容） | 三条全过 |

**补充交叉验证**：搜索实验室与 `/api/search` 对同一 query、同一源子集，输出的每源条数/耗时/错误码必须一致（容差：条数严格相等，耗时不比）。不一致即说明其中一条路径是"装饰性"实现。

## 8. 人工 5 分钟验收脚本（非技术用户可执行）

1. `docker compose up -d` → 等待健康检查通过（≤2 分钟）；首次打开后台要求**自己设置**管理员口令（找不到任何默认密码）。
2. 添加 Brave（真实 Key）+ SearXNG + 1 个 Mock 源 → 三源自检均显示明确结论（错误 Key 的那条必须红）；源列表里"已实现"只有这四类，目录条目单独标注"仅目录 · 未实现"，找不到"支持 30 源"之类文案。
3. 实验室输入 `typescript monorepo`，勾选三源 → 5 秒内看到每源条数与耗时；把 Mock 的 `maxConcurrency` 调到 1、rpm 调到 1 再触发两次，第二次必须看到额度拒绝提示（而非空结果）。
4. 复制 `/api/search` 的 curl 示例执行 → 返回 JSON 含 `results` 与 `source` 字段，无任何完整 Key 字符串。
5. `docker restart` 容器 → 刷新后台：源、Key 掩码、`maxConcurrency=1`、rpm=1、累计调用数全部保留（允许刷出前等 5 秒）。
6. 停掉 Brave（改错 Key 保存）→ 再搜一次：仍返回 SearXNG/Mock 结果，且页面显示失败源与原因码。
7. 打开源列表 → 「已实现」区只有 Tavily / Bocha / Brave / SearXNG / Hacker News / Generic / Mock；点任意"仅目录 · 未实现"条目，**创建按钮灰态**，无"支持 30 源"类文案。
8. 打开 AI Models 页 → 可正常添加模型配置并点"测试"：填**错误 Key** 时测试必须**失败**（返回"成功"即为作弊）；不配模型时回到搜索页用 `basic` 搜一次，结果与配模型前一致。
9. 若已配好真实 Chat 模型：切到带摘要的 mode 搜一次 → 摘要里每个 `[n]` 都能在结果列表找到对应条目；把 Key 改错再搜 → 仍返回结果列表，摘要为空并标"降级"。

*以上 9 步任一步不通过，Phase 1 视为未交付。*
